# Interview log

Running notes from the design interview. This is not an implementation plan. Statements stay in the speaker's terms. Status labels follow `AGENTS.md`: accepted direction, proposal, deferred, or still open.

## Who is describing the system

Andrew has used computers from the VIC-20 and Apple II through IBM mainframes (MVS/TSO), and has lived in Linux, HP-UX, AIX, OS/2, AmigaOS, Windows, macOS, iOS, and Android. Fedora has been the daily machine for much of the past decade. The formative technical interests are operating-system design, computer graphics, and databases, with substantial time on NeXT machines and a lasting attachment to DB2.

The working method is description. He sets direction, takes risks, and expects to be wrong on the way. Agents implement from that description, including areas he has not built by hand.

## Accepted direction

- The operating system is anchored in a database. Its state lives in tables.
- That database aims at DB2's strengths: buffer pools, caching, query optimization, and ACID durability. A write is acknowledged only after it has been written.
- The core is heavy with checking and recovery. The visible surface stays thin.
- Queues are how work is scheduled. The aim is to accept work whether or not anything is ready to run it yet. An application has a queue where messages such as event notifications land. It may have further queues for commands or requests, consumed in FIFO order. A queue is often persisted in the database. A fast path may keep a queue off disk, because writing every submission would be too slow. This may resemble message passing in the implementation. There is no central messaging system whose failure takes the machine down with it. A party that misbehaves is confined to its own queues. Which kinds of work must wait is not known yet, and is not a decision.
- The OS partition holds what a root filesystem holds today, including `/usr`, `/etc`, and `/var`, and it is walled off from the user.
- A separate partition is an ordinary filesystem of the user's choice.
- Removable media, such as FAT32 flash drives, are mounted as real files. People expect files there.
- A read-only boot is a mode the system can enter, including for a kiosk or other turnkey setup. It is not the normal way the machine runs.
- The database registers an application and can run it. Where the bytes are stored is a convenience.
- The machine boots into a place that is already capable. The feel to aim at is a console in the PS3 sense: menus where a choice exists, the computer doing the work it is good at, and a person supplying direction only when a direction is required.
- Startup has stages. QueueOS-Boot is the first program under our control. UEFI launches it. It looks for block devices, finds partitions, and enumerates the QueueOS instances it can boot. It is our C program for the job GRUB does, and it may contain the recovery prompt. Its hardware focus at this stage is locating block partitions. Boot itself shows a readable progress display.
- The landing surface follows the machine. On the first hardware enumeration, a display paired with at least one input device can support a desktop. The input can be a keyboard, a mouse, touch, a microphone, or another input. If that pair exists, Base may launch a Desktop session, unless the system has been told to stay in text, or the previous boot failed before it reached the desktop. In that failure case the graphical pathway is turned off and the boot lands in the text UI. A serial session stays in text. Inside the session, the user can later choose which inputs belong to which display, which displays combine into one Desktop, and their size and position. That configuration can wait. The first QEMU guest is one display, one keyboard, and one mouse. The first interaction, once Base is ready, is that Base launches Desktop. Desktop decides what that screen looks like and what the user can reach from it. Nothing else is required to be running on that first boot.
- A display can be graphical without being desktop-suitable. A 3D printer may offer a small device UI of the LVGL kind, and it may even be HDMI. That landing is a console-style menu. An app can be set as the default on that kind of machine, such as a printer UI in the Klipper family, and then that app is what comes up.
- With no display and no session, there is no UI work to do. The machine runs whatever applications are scheduled to run, including services such as an SSH daemon or a web server. The display and the console menu stay out of the way until a session starts. A device in the RP2040 size class, with no display, is one of these cases.
- An SSH session lands in zsh. From that shell, `queue-os-menu` launches the text UI, and `queue-os-desktop` launches the desktop when it is not already loaded. The command names are the ones he used for those two actions.
- `queue-os-desktop` brings the desktop up across all attached devices that support the desktop.
- QueueOS-Boot's interface should be Lua as well, including a graphical screen. The aim is that it look friendly and that a developer can see it is an ordinary program, not a second GRUB. The drawing path is the firmware framebuffer, the same class of mechanism GRUB uses. UEFI text output is a CHAR16 console with a small color set and a firmware bitmap font. It is not an ANSI terminal and it is not UTF-8. A graphical Boot supplies its own font and draws pixels. WOFF2 is a poor fit for that stage. QueueOS-Boot's interface is a Lua text TUI, including when a framebuffer exists. The limited palette and the required box-drawing glyphs are the creative budget. Mouse support is used when a pointer is present. This is so the same interface can exist over a serial port, on a non-UEFI PC, on Apple Silicon without UEFI, and on an RP2040-class device. A graphical Boot toolkit such as LVGL is not the plan. Lua also remains the candidate for text screens that run after Base. The text console has 16 foreground colors and 8 background colors from a fixed palette. The required box-drawing glyphs have sharp corners. Rounded corners are outside that required set. Machines with no framebuffer, including serial-only and headless boards, stay on the text path. A small C shim would expose that framebuffer, the keyboard, a pointer when the firmware has one, and block reads to Lua. UEFI offers the Simple Pointer protocol for relative mice and the Absolute Pointer protocol for touch and tablet-style devices. Boot would draw its own cursor. A pointer is not guaranteed on every machine. QEMU can supply one. QueueOS-Boot and its Lua screens live where the firmware loads them, so changing them takes an updater rather than an ordinary write inside the running database. Updates to Boot are a place to be excellent. The bit flip was an oversimplification. The partition holds several blocks. A change writes a new block, or overwrites the oldest of a fixed set. QueueOS-Boot enumerates the blocks it can find and selects the latest one that can launch Base. Failure of the Boot program itself is a separate mode from failure of one of those instances. On UEFI, an update writes a new QueueOS-Boot package and, once that package is verified, sets the firmware boot order so the new package is first and the previous package is second. Two packages are the working number. A third package is part of the plan: a rescue image that updates are never allowed to replace. Five copies of Boot are not. The many recoverable versions belong to the OS blocks Boot enumerates, on the database partition, not in the EFI partition. A planning budget of a few megabytes per Boot package is enough. The EFI partition should be sized comfortably, on the order of 64 MB or more, so the package count is not a space problem. QEMU is given two disk files. QueueOS-Database.qcow2 is the database disk and has no filesystem. QueueOS-UEFI.qcow2 is the x86-64 UEFI boot disk: a disk whose EFI System Partition is FAT32 and holds the Boot packages. qcow2 is the host packaging. The guest sees two ordinary disks. Other platforms replace the UEFI disk with whatever their firmware knows how to load. The database file is meant to be shared unchanged across platforms. The notes already say the on-disk format is architecture-independent and that a generation may contain an executable for more than one architecture. Base is one of those executables: each supported architecture has its own Base in the database, which is a reason to keep that executable small. Boot loads the Base that matches the machine it is running on. The first database image ships with only the x86-64 Base. Other architectures are added when those platforms exist. The way there is a test harness that launches QEMU. It starts with a few x86-64 configurations, then adds more QEMU platforms, including Arm64 guests that will run poorly on the Fedora development machine, and only then moves to physical hardware. The initial Boot and Base are almost trivial C stubs. Boot shows a red screen that says `QueueOS loading...` and then calls Base. Base shows a similar red screen that says `QueueOS Loaded`. The test harness creates the image files and updates them when needed. A test is a folder of whatever that run needs. A typical folder has the two qcow2 disks, a chosen OVMF firmware file, and a configuration file that states the machine assumptions, such as q35. One run is serial-only. Another keeps the same disks and firmware and asks for a screen capture of the text interface. Both emit low-level diagnostics when they can, so a failure can be read precisely. Further folders cover other QEMU platforms, such as AArch64, with the firmware and machine configuration those platforms require. The harness calls QEMU on that folder rather than standing up a virtual machine as a separate object. It captures both the serial line and a screenshot when the test can produce them. The concepts come from the Hydrogen test suite in Philement, not a verbatim copy. Hydrogen keeps numbered blackbox scripts and a JSON configuration per variant under `tests/`, and it writes logs and diagnostics under `build/`. QueueOS separates those. `build/` is what we build. `tests/` holds the tests. `results/` holds what a run produces, including the serial log and any screenshot. A run number is a six-digit counter written like `000-000`, incremented each time a test or a suite runs. The output of case `A-001-001` from run `000-001` is `results/000-001/A-001-001`. Unity is used again for C unit tests, and blackbox tests stay separate. Above that, tests are grouped by letter: A image, B build environment, C C unit tests, D Boot, E Base, F MCP, G Console, H Display Manager, and further letters as needed. Inside a letter, a three-digit package can hold on the order of 1000 cases. `A-001` is the example of a q35 package, and `A-001-001` is one check against it, such as a checksum. When the call finishes, the temporary machine is gone. Boot has its own tests for failure modes, including capturing and annotating those failures. Base has many more tests. The first session used to exercise Base is likely an MCP session, so the harness can drive Base directly. The brainstorming notes did not settle this ring. BOOT.md expects three foundational boot stages. BOOTSTRAP.md still asks whether that is two or three. DATABASE.md keeps committed generations immutable, distinguishes preferred from last-known-good, and proposes three small directory slots so a new directory can be written without erasing the previous valid one. The UI is split from the C core. A Lua Boot Script, LBS, reads a JSON description of the UI and may read a separate JSON file for theme and personalization. That script presents the timeouts, defaults, and discovery already described. This is a preference, and the first Boot can still start as a tiny proof before the Lua screen exists.
- zsh is also available inside QueueOS-Boot, as a recovery prompt. It should be able to read some of the database, browse around, and run whatever commands can be made to work there. The boundary is what can usefully be built into that stage. The stage is not there to withhold capability.
- From that prompt, the jobs to aim at are the usual recovery-console jobs. See which variants of QueueOS can be booted. Enable or remove a startup program. Back up the database to another filesystem, or restore a database from one. Change the size of the database partition. Add a filesystem partition. Edit. Check hardware. Enumerate devices. Reach the network. If the stage can get that far, probe displays: choose a default display and set their order.
- A boot variant is another QueueOS the machine can start. Installing 2.0 beside a running 1.0 can mean a separate database, or a separate set of files, and the boot list then offers more than one OS. A failed database integrity check is a reason to boot the previous version. WAL-style writes are managed with something akin to superblocks, and a person can select among those superblocks after corruption or when something should differ between variants. A checkpointing scheme is also in mind, in the spirit of a Windows experiment he places around the Windows 7 era.
- QueueOS-Console is the landing when a desktop is not possible. It provides a text hardware manager, full zsh, JSON and text editors, and the other tools needed to get around without a desktop. The earlier text-menu list still belongs here: Lua scripts, a commander-style file browser, reboot and restart, and room to grow.
- Diagnostic text can be available to someone who wants it. People who do not want it are not required to watch it.
- QueueOS is its own system. The early nudge was the existence of projects like Omarchy, not their taste or their stack.
- The system has users and groups, in the spirit of Linux and systems like it. Authority is expressed as rights. Scheduling an application to run is one right, and most people are expected to have it.
- The first people it is for are those who want to play with a different OS. They do not need broad application support. That includes people building appliances, such as 3D printers, and people interested in novel designs. Omarchy users are one possible early audience. The userbase is expected to widen as the OS becomes more capable.
- Those experimenters and early adopters are mostly people already running Linux who can run KVM and QEMU, the same way the development platform does. Playing with QueueOS, at first, means running it as a guest.
- The guest is a generic x86-64 PC. More than one QEMU machine family should be able to run it. On QEMU 10.2 the generic families are `pc` (i440FX + PIIX, the default) and `q35` (Q35 + ICH9). The many `pc-i440fx-*` and `pc-q35-*` names are versioned snapshots of those two, not further machines. `microvm` and `isapc` exist and are not generic PCs.
- Firmware work starts with UEFI. Other boot pathways stay open for exploration.
- The executable names are hypothetical. QueueOS-Boot reads the instance from a block device without the SQL engine. While enumerating, it checks that the blocks needed to launch QueueOS-Base are present, that the checksums match, and that QueueOS-Base itself is available. The Base executable is small, under about 500 KB, so Boot retrieves it from the partition during that enumeration. That size is the executable Boot must be able to fetch. It is not a claim that a DB2-sized engine fits in 500 KB. A separate calibration: a Hydrogen project with about 100,000 lines of C compiled to about a 200 KB executable. That shows a large amount of C can pack into a small image. It is not a claim that the two systems are comparable. A normal boot writes the outcome back to the block partition. QueueOS-Base sets the criteria for a successful boot. The record lets the next Boot see whether the last attempt to start that instance succeeded.
- The default instance is the latest by timestamp, not by version number. If that latest instance's most recent boot failed, Boot does not start it automatically. It stops, highlights the most recent successful boot, and starts a timer that launches that choice if nobody intervenes. The point of that record is to avoid an endless boot and crash loop.
- A successful boot is not fully settled. The working presumption is that Base has finished the initial database load, finished buffer-pool and cache work, finished hardware enumeration, and is ready to serve sessions. Those sessions include MCP, Desktop, Console, Remote, and a user-supplied session such as a 3D-printer Klipper screen. Reaching that ready state is the presumption. A crash before it is the failure being guarded against. A session that crashes after Base is ready does not, by itself, make that boot a failure. A working sketch of Boot's layers is Phase 1A, locate the boot device; Phase 1B, load the data; Phase 1C, launch QueueOS-Base. These are mode names. The names and the layering are a sketch.
- QueueOS-Base is the kernel of the selected instance, in the process 0 role. It is database-aware: it initializes the database engine, starts loading queries, and may pre-cache buffer pools. It enumerates the rest of the hardware. It identifies displays, including whether they have been used before and whether display preferences exist. It knows more about the machine than QueueOS-Boot does. How much of the engine lives inside that executable is unsettled. One possibility is that Base launches separate database worker threads and manages buffer pools. Once Base is running, it provides its full services to QueueOS-Console and to any other caller.
- The first foray is intentionally small at the edges and heavy in the database. QueueOS-Boot starts as something QEMU can launch, with output a test can recognize as our code. The first days of Base ask whether it is running, whether that can be seen, whether QueueOS-Console can interact with it, and whether a primitive QueueOS-Desktop can be launched. The database engine inside Base is the large early body of work. He expects the major initial showstoppers to be there, and he expects that work to pay off sooner rather than later.
- QueueOS-Desktop is separate from Base. It is the parent task of the window manager. More than one may run. A machine with several displays and several keyboard and mouse pairs might be used as several seats, and a desktop might also serve a remote graphical user. Once Base has launched a session, its concern for that session ends. The same handoff applies to Desktop, Console, MCP, Remote, and a user-supplied session. Each one owns what happens after launch, including its own crash handling. Base is deliberately minimal here and is not the nanny for those sessions.
- QueueOS-Console and QueueOS-Desktop are ordinary userspace processes, nothing special. Base runs first. It is the kernel and the running OS. It then starts whichever of those processes the machine needs. They call into Base the way any other process does.
- QueueOS-MCP sits on that same tier. MCP integration is a key part of the system, so the models and tooling used to build QueueOS can jack in and see what is going on without a special setup step. The interface is an ordinary MCP tooling surface. The caller is treated as another user, with rights, and access may require a token exchange. A connected model can help troubleshoot, launch or stop applications, conduct the OS, or diagnose, depending on what it is asked and what it is allowed to do. With no extra rights, the caller gets a read-only view that is safe to share publicly: what the instance is, basic resource utilization, and enough for the caller to decide whether to request more access. An authentication pathway is offered for that request. This role was not written in the brainstorming notes. QueueOS-Remote sits on that tier as well: a VNC, RDP, or NX style service that launches and serves a Desktop-style instance optimized for remote viewing, when that path is more performant than rendering a local desktop and broadcasting it.
- Boot, Base, and Desktop are written in C at this stage. The platform C calling convention is how functions call each other inside one program. It is not the design of a call that crosses from a process into Base.
- A call from a process into Base is aimed at a queue submission. The caller searches the available queues by name and tags. One sketch of a search is `QueueOS-Desktop;First` or `QueueOS-Console;Active`. The result is a list of matching objects, such as a user or a process, together with their qids and tags. The caller decides, by its own rules, which qids to use. A search may return only one match. QueueOS-Base is singular for now.
- Tags name the kind of queue. Base might offer a `launch` queue and a `cancel` queue, and callers add work there to start or stop something. Another application may publish entirely custom queues. Each queue decides whether it persists and what performance it needs.
- Later, several QueueOS instances may know about one another. The examples are a batch of Raspberry Pis, a network of x86-64 machines, or a mix of those with old MacBooks from around 2015. The same queue call can carry a cluster identifier and a hostname, and then address a queue on another machine. QueueOS-Base can be plural in that setting. An instance may belong to more than one cluster. By default it is a cluster of itself. Omitting the cluster parameter means the local host. Members may share information with reachable peers through mDNS or through routable links. One sketch of finding each other is an mDNS announcement that an MCP endpoint is present. Trust between members stays deferred.
- A later aim is Apple hardware that Apple no longer supports, such as old MacBooks that cannot run the current macOS or receive security updates. Those people are looking for a simpler experience that is not a less performant one.
- There is a list of rights. Users, files, applications, services, processes, threads, and later kinds of objects can be associated with those rights. Finding what an object may do is a join against that table.
- Some rights belong to one object. A user who may print is the example. Other rights associate more than one object, such as a user and the files that user may edit. Which rights take which shape is an experiment, and it is not settled.

## Proposals

- A path such as `/queue-os` may present ordinary files and folders while the stored objects are blobs. This is optional, for people who expect that shape.
- System components, vetted applications, and OS-level integrations may live in the database.
- Unvetted applications, tinkering, and development builds may live outside it.
- If a userland emerges, those applications go on the filesystem.
- The desktop to meander toward is in the neighborhood of Plasma, the OS/2 Workplace Shell, and what he has heard about BeOS. The aim is to reuse the lessons of those environments. Reinventing them is not a goal.
- A major version, such as 2.0 beside 1.0, gets its own database. A minor version might be a variant flag on the tables, in the spirit of tenants: making a new variant duplicates the relevant rows and selects that variant. He expects other options to stay in play.
- Work can land on an application's queue while that application is not running. This was a leaning yes, not a firm rule.
- Queuing work and starting an application are separate. Wake-on-arrival is an option an application can have, not a requirement. An application can also be started by a user action, or by an event rule, such as its queue passing a pending-item threshold. Further event rules are unsettled. An application might start, do its work, and then exit completely.
- When applications start is itself table data. That table covers the jobs people use cron and the Windows startup registry for: at startup, at login, at a time of day, and similar cases. The OS has its own mechanisms, akin to database triggers, that decide when a launch happens.
- Groups may be nested. One sketch is org, then department, then team, then user. How many tiers are needed is unsettled. Rights are given to groups.
- People and machines are objects. Users may be local to this instance, part of the larger network, or the public. Peers are systems in the same cluster. Systems are machines not in that cluster yet. Some objects will have the right to grant a right to another object. Escalation and inheritance are expected. The implementation waits until more of this is working.

## Deferred

- The policy for which applications live on which side of the wall. Registration and the ability to run them are enough for now.
- Whether some future disk is itself the database, and how foreign filesystems would then be addressed.
- Treating a read-only OS partition as the permanent arrangement.
- Using NeXT or iOS as a template. They are the nearest ancestor he will name, and he has set them aside as something to copy.
- How installed versions share data, including the major-database and minor-variant ideas above. Sort that out later.
- Further detail of how cluster members trust one another. Finding each other has a sketch: an mDNS announcement that an MCP is present, then a public read-only query of what that instance wants to contribute. A lone instance is still its own cluster, and a call with no cluster parameter stays on that host.
- Who grants a request for more than the public MCP view, and the mechanics of granting, escalation, and inheritance. The object sketch above is enough until more of it is working.
- How Desktop responds after a crash. Likely options include a login, a safe-mode desktop, or a desktop without widgets. Those are Desktop's problem, separate from Base.

## Proposals added 2026-11-25

Status: proposal. These notes are the interview. They are not the plan. Plan 003 was marked ready on 2026-11-25 and is the slice that builds them. Where the plan and these notes differ, the plan is the one to build.

- The database disk has no filesystem. Ten 4 KiB slots sit at the start. Slot 1 is byte 0. Each slot is a JSON object, then a newline, then a line `sha256` and 64 lowercase hex digits. The hash is of the JSON bytes only, so it does not depend on key order. The rest of the slot is zeros. An empty slot is `{}` and a matching hash. Pictures stay out of the slot.
- `"OS":"QueueOS"` is a sanity check, not a secret. A generation also carries a name, a version, a publication timestamp, and pointers to binaries. A pointer has a role, an architecture, a byte offset from the start of the disk, a length, a sha256, and a `"file"` label such as `Base.efi`. The label is for the Explore view. It is not a path. This disk has no directories. The same bytes can be shared by more than one slot, and they share that label.
- If the JSON parses and the hash matches and OS is QueueOS, the slot is a candidate. If it parses and the hash does not match, the list shows UNSAFE and Boot does not start it. If it is not JSON, skip it as unreadable. `{}` with a good hash is empty. A good hash with some other OS is not a QueueOS generation.
- The list shows all ten slots, in slot order. The framed QueueOS mark is centered at the top of one stack, the slots sit in the middle in a column the width of that mark, and Explore and Launch sit under the list. Spare rows and columns center the whole stack. A terminal too small for the frame uses the one-line word and scrolls the slots. The mouse selects a row. The first selection is the newest launchable candidate by publication timestamp, or slot 1 when none can launch. If that row can launch and there is no keyboard or mouse activity, a 10 second timer launches it. Activity starts the 10 seconds over. Explore pauses the timer. An UNSAFE or empty row is not what the timer starts.
- Explore replaces the list with a scrollable pretty view of that slot's JSON, and replaces the buttons with Back. The pretty view is not written back. Editing waits.
- Automatic boot uses the newest candidate that names a Base for this machine. The architecture token is the one this Boot was built for, `x86-64` on the first image. There is no UEFI call that answers the question. The same token is what a later non-UEFI Boot would use.
- After the ten slots, the binaries live in a range whose size can be tuned later. The database body stays past that range so later body bytes do not slide when a Base or a picture is added. The first image leaves that body empty and puts one x86-64 Base in the boot range. Pictures are blob entries with role `thumbnail`, legal and absent for now. They are not base64 inside the JSON. UPX is out of this conversation.
- The writer, later, reads all ten slots, gathers the binaries still named, and rewrites that set. An identical sha256 reuses one copy. New bytes go in a free gap or at the end of the boot range. Offsets a slot still names stay put. If nothing fits, the publish stops. A reorg happens only when requested, and it does not move the body. Replacing the oldest slot drops that record. The next rewrite can drop binaries nobody names. Do not overwrite the only good generation in place before the new slot is committed.
- Boot links Lua and Jansson into the executable. Nothing is loaded at runtime. Jansson reads the ten slots. Lua draws the list, runs the timer, and pretty-prints Explore. The firmware has no libc, so malloc and free have to be the UEFI pool. That heap is not part of the host screen.
- For trying the screen, a host program runs the same list against a disk image and does not launch Base. A qcow2 is converted to a temporary raw file, which is the byte layout Boot sees. `lua tests/boot-tui.lua` with no image shows ten empty slots. Launch prints the chosen Base and returns. The firmware Boot is still the ESP scaffold.

## Plan 004 interview

Status: accepted for plan 004. `plans/004-body-record.md` was marked ready on 2026-11-25 and is the active slice. Nothing in it is built. The answers below are the cluster from 2026-11-25, after plan 003 closed.

- The slice is one record in the database body, past 8 MiB. A later boot reads it back. Queues, SQL, and buffer pools stay out of the slice.
- The record remembers that this boot stored it: a stamp and the slot number. Name and version stay in the slot. The slot's `booted` line stays the publisher's completion mark.
- Base reads the old record and prints it on the serial line, then writes the new stamp and slot, then prints `QueueOS Loaded`. The first boot has nothing to read, so it stays quiet, writes the record, and prints Loaded. Boot still only reads slots.
- The page is two text lines. `stored STAMP slot N`, then `sha256` and 64 hex digits of that stored line. The rest of the 4 KiB page is zeros. Zeros, a bad hash, or a bad stamp mean there is no record. Base stays free of Jansson. The page is this record's shape. A later plan can replace it with a table.
